03 · the approach

Pedro's L3 Law.

Level 3 agentic engineering is not using a coding assistant more often. It is a different way of organising the work: engineers spend less time directing code changes and more time designing the specifications, constraints and evaluations that produce reliable code. At L3, specs, not prompts, drive the code; L4 adds production feedback to the specs. Yes, I named it after myself, so that nobody else gets the blame.

the specs loop · humans

Use as many rich, iterative prompts as you need to create the specifications.

the implementation loop · agent

Then with ONE prompt: generate the code and associated unit tests.

risk tiers

Spec depth follows risk

A copy change needs behaviour, scope and acceptance tests. A public contract or a security control also needs ADRs, observability, rollback and a named human approver.

the oracle

Not the generated unit test

Human-approved acceptance tests (the oracle) and fitness functions (automated architecture checks) judge the code. CODEOWNERS, CI and sandbox permissions lock them, not a polite line in a prompt.

regeneration

Code is disposable output

Implementation is the output of a versioned spec and a controlled process. Fix the spec, discard the slice, regenerate, and run the same gates again.

traceability

Every change has a pedigree

Each pull request records the spec version, ADR, prompt template, baseline commit, agent, model and evaluation report, so a run can be reproduced and judged.

parallel agents

Shared specs, many agents

Parallel agents only help when they share durable contracts and evaluation criteria. Otherwise you get five interpretations of one problem.

health metrics

Measure the system, not the prompts

  • Spec traceability% PRs
  • Corrective promptsper PR
  • Regeneration success% gates
  • Post-merge defectsescaped

04 · foundation

AI amplifies what is already there.

Before agents, I spent over three decades writing software and teaching teams how to keep it easy to change: test-driven development, refactoring, domain-driven design and hexagonal architecture.

That is the ground this work stands on. An acceptance test is an oracle. A bounded context is a context boundary. An ADR is provenance. Teams with strong engineering get far more out of AI; teams without it get their problems faster.

The same ideas are written down as guidance for other teams: service classification, seam refactoring, decision records and fitness functions.
